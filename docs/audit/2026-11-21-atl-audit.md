# ATL accuracy audit, 2026-11-21

Read-only sweep of the fork (main at `8df2fa7b`, before the drawable-alpha merge) for places where ATL differs from Android: AOSP code commented out, silent no-ops, ignored attributes, wrong defaults, shared state, Java/native mismatches. ### H1. requestPermissions never delivers onRequestPermissionsResult; checkPermission denies all unlisted (incl. normal) permissions
`src/api-impl/android/app/Activity.java:724` · app-content-os · silent_noop · confidence high

```
public void requestPermissions(String[] permissions, int requestCode) {
	Slog.w(TAG, "requestPermissions(" + Arrays.toString(permissions) + "): not handled");
}
// PackageManager.checkPermission default:
default:
	System.out.println("PackageManager.checkPermission: >" + permName + "< not handled\n");
	return PERMISSION_DENIED;
```

- **Android:** AOSP always answers with onRequestPermissionsResult(requestCode, perms, grantResults), which AndroidX ActivityResult permission launchers depend on. Normal (install-time) permissions declared in the manifest, such as INTERNET, WAKE_LOCK, VIBRATE, FOREGROUND_SERVICE and RECEIVE_BOOT_COMPLETED, are reported GRANTED.
- **Impact:** Apps that check a permission (e.g. POST_NOTIFICATIONS, CAMERA, or any normal permission) see DENIED and call requestPermissions. The callback never comes, so features wait forever or stay disabled (notification setup, camera/QR scanning, file import) with no error.
- **Fix:** In requestPermissions, post to the main looper a call to onRequestPermissionsResult(requestCode, permissions, results), where results come from checkSelfPermission per entry. In PackageManager.checkPermission, return GRANTED for permissions declared in the app manifest with protectionLevel normal.
- **Verifier:** Activity.requestPermissions (line 724) only logs. PackageManager.checkPermission returns DENIED by default for everything except a handful of storage, network and C2DM permissions, which Context.checkSelfPermission reaches through checkCallingOrSelfPermission. Apps asking for permissions outside that list never get onRequestPermissionsResult.

### H5. Intent.resolveActivity returns null for implicit intents ATL can actually handle (VIEW URL, SEND)
`src/api-impl/android/content/Intent.java:890` · app-content-os · constant_instead_of_state · confidence high

```
public ComponentName resolveActivity(PackageManager pm) {
	return component;
}
```

- **Android:** AOSP resolves the intent through PackageManager.resolveActivity and returns the handler's ComponentName. The documented pattern is `if (intent.resolveActivity(pm) != null) startActivity(intent); else showNoAppToast()`.
- **Impact:** For implicit intents such as ACTION_VIEW with an http(s) URL, ACTION_SEND or mailto, the method returns null even though ContextImpl.startActivity would open them through portals. Apps show "No browser/app found" or silently do nothing for Open link, Share and Email. ATL's own PackageManager.queryIntentActivities special-cases http VIEW, so the two disagree.
- **Fix:** Call pm.resolveActivity(this, MATCH_DEFAULT_ONLY) and return its ComponentName. Make PackageManager.resolveActivity return a synthetic ResolveInfo for the intents startActivity handles externally (VIEW with data, SEND, CHOOSER), as queryIntentActivities already does for http.
- **Verifier:** Intent.resolveActivity (line 890) returns the component field, which is null for implicit intents. Meanwhile ContextImpl.startActivity does handle SEND and any intent with data (nativeOpenURI or file open), and PackageManager.queryIntentActivities special-cases http VIEW. The 'resolveActivity != null' guard therefore wrongly blocks working actions.

### H6. Theme.applyStyle/setTo never update ThemeKey, so every Theme shares one drawable/ColorStateList cache bucket
`src/api-impl/android/content/res/Resources.java:1255` · app-content-os · shared_state · confidence high

```

	...
	mAssets.applyThemeStyle(theme, resid, force);
}
public void setTo(Theme other) {
	getAssets().copyTheme(this.theme, other.theme);
}
...
private final ThemeKey mKey = new ThemeKey();   // never appended to
```

- **Android:** AOSP Theme.applyStyle calls mKey.append(resId, force) and setTo copies mKey. ThemedResourceCache (used by loadDrawable via mDrawableCacheInternal.put(key, theme, cs) and by the ComplexColor cache) partitions cached entries by that key, so a drawable or ColorStateList resolved against one theme is not reused for another.
- **Impact:** All non-null themes have an empty, equal ThemeKey. A drawable or color selector whose ?attr values were resolved under one theme (e.g. the activity theme) is handed to views under a different theme (ThemeOverlay toolbar, dialog theme, a second activity with another theme). - **Fix:** In Theme.applyStyle add mKey.append(resid, force). In Theme.setTo add mKey.setTo(other.getKey()) (and recompute the hash code in ThemeKey.setTo as AOSP does). Implement rebase() from the key if needed.
- **Verifier:** Theme.applyStyle (Resources.java:1255) only calls mAssets.applyThemeStyle, and setTo only calls copyTheme. Neither touches mKey (line 1505). getThemedLocked in ThemedResourceCache keys entries by t.getKey(), so every theme shares the empty key (hash 0, equal). loadDrawable reads and writes mDrawableCacheInternal and mColorDrawableCache with the theme, so a drawable resolved under one theme is handed to another.

### H15. Canvas.drawLines steps by 1 float instead of 4, ignores offset+count and reads past the array
